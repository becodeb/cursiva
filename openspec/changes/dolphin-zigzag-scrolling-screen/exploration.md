## Exploration: dolphin-zigzag-scrolling-screen (docs/13 §8 row G)

### Current State

**Sector / registration.** `estanque` already holds 8 `adventureIds` (duck ×4 + medusa ×4) in `client/src/zoo/sectors.ts:355-364`. `client/src/zoo/adventures.ts` keys backdrops/intros through a per-**adventure** `AdventureId` (not per-sector) precisely so one sector can carry more than one backdrop — `montanas` already does this for `sheep`/`llama` (two different backdrop rows, `client/src/zoo/backdrops.ts:114-132`, both `art: SECTOR_BACKGROUND_ART.slope`/`.range`). The identical pattern lets `estanque` carry a third adventure (`dolphin`) with the SAME `SECTOR_BACKGROUND_ART.lagoon` art but its own `AdventureBackdrop` row (own `corridorRows`, own `channel`/`ink` if the panning window changes what colours the corridor crosses). No "costa" sector exists in code or art — `docs/12`'s map PNG has fixed, already-drawn sectors and there is no `costa` hit/fog/backdrop anywhere; docs/13 §3's "pueden pedir un sector propio... si el estanque queda cargado" was explicitly left undecided "cuando lleguen" — they've now arrived, and nothing in the codebase or art pipeline supports a new sector without new map art. **Recommend estanque is correct and no new sector.**

**Lagoon backdrop, measured (not estimated).** From `duck-undulations-and-sector-backdrop`'s post-design "Measured facts" addendum: `fondo laguna.png` quiet band is source rows 201–818 → viewBox `[97.6, 499.1]`; `corridorRows` registered as `{top:135, bottom:889}` (the widest duck channel, `duck-trail3`'s 55…545 pushed through `imageToViewBox`); `brightest` under that whole range is `#b4c5d0` (luma 193) — the water itself, no brighter pixel anywhere in it (0% pixels > luma 196). `SHEET_PAPER` (luma 251.7) clears the `docs/09 §4` 55-luma law by 58 (not the 55-ish margin some documents guessed). **Channel token = `SHEET_PAPER`, unchanged from the duck row** — a dolphin corridor can safely reuse it AS LONG AS its channel stays inside `corridorRows {135,889}` in viewBox terms (i.e. `y ∈ [~97.6, ~499.1]` after `viewBoxToImage`); a channel that reaches further vertically needs new sampling before the same `SHEET_PAPER` claim can be trusted (§3.5 of that design is the exact recipe: extend `corridorRows`, rerun `build_art.py`, re-assert the luma law, never eyeball).

**The viewBox is a STATIC rectangle today — there is no camera.** `client/src/canvas/TraceCanvas.tsx:1003` renders `viewBox={`0 ${viewBoxY} ${viewBoxWidth} ${viewBoxHeight}`}`, and `viewBoxWidth` (default 1000, `:59,616,739`) already WIDENS automatically when a level's path needs more paper — `client/src/levels/buildLevel.ts:137-154`'s `layOutPaths` computes `viewBoxWidth = max(MIN_VIEWBOX_WIDTH, pathSpan + margin)` and centres the path in it; this is exactly the mechanism word-building levels (`f4-la`, `f5-mama`) already use for long combined letters. BUT `LevelPlay.tsx:1616` renders `TraceCanvas` with `fit="contain"`, so a wider viewBox is shown **shrunk to fit**, all at once (`preserveAspectRatio="xMidYMid meet"`) — never panned. A longer dolphin route authored the "just widen viewBoxWidth" way would ship VISUALLY SMALLER strokes, which directly fights `docs/13`'s own point ("sostener el movimiento más tiempo" — sustaining the SAME movement longer, not a shrunk one). **`docs/13` §4's own row for dolphins is explicit and literal: "Desplazamiento de pantalla (viewBox que avanza con el trazo)" — this is a real, new mechanic, not a relabelling of the existing wide-viewBox feature.**

**The engine already has the exact idiom a panning camera needs.** `TraceCanvas.tsx:843-936`'s single rAF loop is the "60fps strategy": it mutates DOM attributes directly on refs every frame — `path.setAttribute('d', d)` for the live ink (`:887`), `el.setAttribute('transform', ...)` for hazards (`:904-907`) and for the carrier (`:918-921`) — with **zero `setState` per frame**. `svgRef` (`:762`) already points at the `<svg>` root. Adding a `viewBoxX` (camera x-origin) driven by `svgRef.current.setAttribute('viewBox', ...)` inside this SAME loop, computed from `rendered[rendered.length-1].x` (the exact expression already used for the carrier's head, `:917`), is a drop-in extension of an established pattern, not a new one.

**Pointer input survives panning by construction.** `client/src/canvas/useTraceInput.ts:49-54`'s `screenToViewBox` calls `svg.getScreenCTM()` FRESH on every `pointerdown`/`pointermove` (never cached), so a changed `viewBox` attribute is picked up on the very next pointer event with no extra wiring. The only open risk is ORDERING: the camera pan (rAF-driven) and pointer events (input-driven) are not synchronized, so a fast stroke could sample a `pointermove` against a viewBox that is one rAF tick stale. This needs a design-time test/measurement, not a rewrite — it is the same class of risk `resample.ts`/`corridorTrack.ts` already manage for other per-frame vs per-event mismatches.

**`levelStart` and `carrier` are already general** (paso F repair, `buildLevel.ts:66-69`, `LevelPlay.tsx:1186`: `const startMarker = target.start`). A `kind: 'path'` dolphin level needs NOTHING here — `target.start = target.polyline[0]` exactly as every routed level already gets, byte-identical.

**"Sin tocarlos" — touching a dolphin, in engine terms.** Two existing, real precedents, and they are NOT the same mechanic:
1. **`vertexArt`** (`client/src/levels/vertexArt.ts`): static decoration standing at route peaks (sheep/llamas), placed via `routeApexes(polyline)` which finds only **local MINIMA in y** (crests, `:19-34`, `cur.y < prev.y && cur.y < next.y`). It does **not** find troughs. The schema (`docs/referencias/delfines-zigzag.png`) shows dolphin arcs both ABOVE crests and BELOW troughs, alternating — `routeApexes` as written cannot place the trough half. A new helper (or a parametrised `routeApexes` that also returns local maxima) is needed, or a different construction entirely (e.g. computing both extrema straight from the wave generator's own authored per-cycle geometry, the way `waveCrestRadius`/`peakRidgeCorridorLimit` are computed from generator literals rather than by scanning the polyline).
2. **`obstacles` + `hazardArt` + `resetOnContact`** (`catalog.ts:1637,1644,1607`, the medusa's `f2-agua4` starfish): a MOVING hazard that must be timed/avoided, contact restarts the run. This is a real "don't touch it" mechanic already wired end-to-end (`Obstacle` type, `levels/obstacles.ts`, `HAZARD_STARFISH_ART`, `TraceHazards`).
`vertexArt` reads as pure narrative decoration (sheep/llamas never reset the run on contact); `obstacles` reads as a real gameplay hazard. Docs/13's own wording ("pasa entre ellos sin tocarlos... rítmico y sostenido") is closer in SPIRIT to a corridor that simply threads between fixed decorations — like `vertexArt` — where "not touching them" is achieved by the corridor's own geometry (the dolphins sit outside the drawn channel, so staying inside the channel already keeps the child clear of them), rather than a literal hazard/reset mechanic. This is a genuine open design fork, not a codebase gap: **does "sin tocarlos" mean (a) purely narrative/decorative — the wave's own walls already keep the child off the dolphins, reusing `vertexArt`'s pattern with a new trough-aware placement helper — or (b) a literal touch-triggered consequence via `obstacles`/`resetOnContact`, treating the dolphins as static hazards (`travel: 0`)?** Recommend (a) for consistency with sheep/llama precedent and with docs/13's own general rule ("los obstáculos aparecen después, nunca al comienzo" — dolphins are still early/mid progression, phase 1); flag (b) as the alternative if the author wants literal contact consequences.

**Demo.** `LevelConfig.demo?: boolean` (`types.ts:124`) drives `DrawDemo` in `LevelPlay.tsx` (`playDemo = !!level.demo && guideLevel === 'full'`, `:796`) — a framer-motion `pathLength` animation over `target.paths`. All four `duck-trail*` levels already ship `demo: true` (`catalog.ts:583,667` etc.) even though `docs/13` §5 item 2 says demo is only "cuando el movimiento es nuevo" — this mismatch is already a recorded, unresolved Open Question from the duck design, carried forward, not something row G invents. For dolphins the demo is EXPLICITLY requested by docs/13/14 ("antes de empezar, una animación breve y discreta muestra el movimiento esperado") and the movement genuinely IS new (the scrolling corridor), so `demo: true` is well-justified here regardless of that open question. **New risk specific to this row**: the existing `DrawDemo` mechanism animates a dot along `target.paths` inside a STATIC viewBox — it has no notion of camera panning. If a panning camera is added for the `kind:'path'` corridor mechanic, the demo must either (i) run entirely inside the un-panned first "window" of a level short enough to fit (viable for dolphin1/dolphin2, see progression note below), or (ii) be extended to drive the SAME camera pan in sync with the animated point, which is new code with no existing precedent.

**Phase-1 guard.** `catalog.test.ts:580-598` (`level.kind !== 'path'` are skipped) requires every phase-1 **path** level's polyline to have vertical span > 300, `minY < 180`, `maxY > 420`, and to stay inside `y ∈ [0,600]` — this is a Y-only guard, unrelated to how wide (X) the level is. A dolphin `kind:'path'` level at phase 1 must still clear this guard, exactly like the ducks; it says nothing about horizontal length or panning, so it does not conflict with a scrolling mechanic.

**Progression clue in docs/13/14 that de-risks this row.** `docs/13` §2's own four steps are: "pocos delfines y separación amplia → más delfines → **recorrido desplazable** → sostener el patrón más tiempo." The scrolling/panning mechanic is explicitly introduced at STEP 3, not step 1. Steps 1–2 can therefore ship as an ORDINARY corridor level inside the standard 1000-wide sheet (few dolphins, wide separation — reusing 100% of existing engine, zero new code), and only steps 3–4 need the new camera. This mirrors the duck family's own cycles-1/2/3(+taper) escalation and the bee family's stops-1/3/3/3 escalation — the established "first rung stays inside the existing engine, later rungs carry the new mechanic" pattern from every prior row (C: peakRidge only from sheep; D: reveal grid only for entrance/night; E: drag+art-corridor only for snakes; F: waypoints only for bees).

### Approaches — the camera mechanic (the one genuinely new engine decision)

1. **`viewBoxX` prop, mutated imperatively per-frame inside the existing rAF loop** (extends `TraceCanvas.tsx:843-936`'s established idiom — same pattern as ink/hazard/carrier attribute writes).
   - Pros: reuses an idiom already proven at 60fps with zero new `setState`; pointer mapping (`useTraceInput.ts`) needs no change at all, since `getScreenCTM()` is read fresh per event; keeps visual scale constant regardless of route length, honouring "sostener el movimiento" pedagogically; isolates the new risk to exactly 2 of 4 levels if dolphin1/2 stay unpanned (per the progression note above).
   - Cons: the demo animation (`DrawDemo`, framer-motion) has no existing hook to also pan in sync — needs new code for dolphin3/4 if they carry `demo: true`; a fast stroke could sample a `pointermove` against a one-tick-stale viewBox (needs a design-time measurement, not assumed safe); component/SSR tests can only see the INITIAL viewBox (same limitation the live ink path already has, and already an accepted testing convention in this repo).
   - Effort: Medium — one new prop, one new per-frame computation (clamped camera-x from the current stroke's furthest point or the carrier position), no change to any other subsystem.

2. **Do not pan; just widen `viewBoxWidth`** (the mechanism `layOutPaths`/word-building already has, zero new code).
   - Pros: trivial, reuses 100% existing code, no new risk.
   - Cons: **directly contradicts** `docs/13`'s own literal spec for this row ("viewBox que avanza con el trazo") and its own pedagogical point (sustaining the same-scale movement longer); with `fit="contain"`, a long route simply renders smaller, which is the opposite of the intended difficulty curve. Not recommended as the row's actual mechanic, though it is exactly right for dolphin1/2 which do not need panning at all.

3. **Pan via CSS transform on a wrapper element, leaving the SVG's own `viewBox` at the full route's fixed `0 0 W 600`.**
   - Pros: separates "camera" from viewBox math entirely.
   - Cons: introduces a second, parallel sizing system (CSS container width vs SVG intrinsic viewBox units) that every other level in this engine deliberately avoids (`docs/09 §3`: "sizes are in viewBox units"); `getScreenCTM()` does still account for ancestor transforms so pointer mapping would still work, but this is a materially bigger and less idiomatic change than option 1 for the same outcome, and it complicates `fit="contain"`'s existing `preserveAspectRatio` responsive-sizing story. Not recommended.

### Recommendation

Adopt **Approach 1** (imperative `viewBoxX` camera prop inside the existing rAF loop), scoped **only to dolphin3/dolphin4** per the progression's own text — dolphin1/dolphin2 ship as ordinary `kind:'path'` corridor levels with zero new engine code, exactly mirroring how every prior row's first rung stayed inside the existing engine (peakRidge only from sheep, reveal only from entrance, waypoints only from bees). This derisks the one genuinely novel piece of engineering in the whole row down to 2 of 4 levels, and lets it be built/tested against a small, isolated surface (one new TraceCanvas prop, one LevelPlay computation) before the demo-panning question is even reached. The dolphin decoration placement (crests AND troughs, offset outward) needs a new small pure helper alongside `vertexArt.ts`, not a rewrite of it. Sector = `estanque`, backdrop = `SECTOR_BACKGROUND_ART.lagoon` reused with a new `AdventureBackdrop` row keyed by the new `dolphin` `AdventureId` (not by sector) — this is the exact, already-proven `montañas` (sheep/llama) pattern, so no new sector, no new sector art, and the `SHEET_PAPER`-channel luma-law finding from the duck row is directly reusable AS LONG AS `corridorRows` is (re-)measured to cover whatever vertical extent the panned dolphin corridor actually reaches — do not assume the duck's own `{135,889}` covers it without checking.

### Risks

- **The camera-vs-pointer-event ordering risk is unverified.** No test in this repo exercises a per-frame DOM mutation racing a per-event pointer read; this needs an explicit design-time measurement or an accepted, named tolerance, not silent assumption.
- **The demo-panning gap has no precedent to copy.** If dolphin3/dolphin4 keep `demo: true`, the design phase must decide whether the demo stays confined to an unpanned preview or gets new camera-sync code; either is a real, unscoped decision, not a detail.
- **"Sin tocarlos" is a genuine, unresolved authoring fork** (decorative/vertexArt-style vs. literal hazard/`resetOnContact`) — the codebase supports both mechanics but they carry very different consequences (fail-and-restart vs. none), and docs/13/14 do not disambiguate.
- **The lagoon's `corridorRows`/`brightest` luma-law finding is corridor-shape-specific.** It was measured for the DUCK's channel extent; a panned dolphin channel that reaches new vertical territory must be re-sampled through `build_art.py` before reusing `SHEET_PAPER` — this is a `npm`/Python pipeline step this exploration could not run (no Bash tool available in this execution context), so it is a NAMED, not resolved, open item for `sdd-design`/`sdd-apply`.
- **A backpack item for `estanque` is undecided** by any existing doc or precedent (the duck row shipped without one) — needs an explicit author decision, not a default.
- **No Bash/shell tool was available to this exploration**, so `scripts/art/png.py` measurements of `art-source/delfin.png` (exact alpha bbox, dominant fill colours, outline chroma) could not be run directly; the evidence used instead is the ALREADY-BUILT, ALREADY-TESTED `client/public/art/sector-dolphin.png` and its passing `artHierarchy.test.ts` assertions, which is strong indirect evidence the source art is clean, but is not the same as a fresh direct measurement.
- **This agent had no Write/Edit tool in its execution context**, so `openspec/changes/dolphin-zigzag-scrolling-screen/explore.md` could not be written to disk. The full exploration content is saved to Engram (`sdd/dolphin-zigzag-scrolling-screen/explore`) and returned inline below; the orchestrator or a subsequent phase with file-write access should materialize the openspec file from this content.
